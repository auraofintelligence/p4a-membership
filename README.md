# P4A: People & possibility

A working custom membership and civic CRM foundation for **P4A the Purple Party for Australia**, built on 7 November 2026. It connects people, groups, projects, reviewable priorities and voluntary contribution. The application is separate from the existing civic websites and the committees project. It is the developing people, learning, collaboration and governance layer, not an operational political-party register.

**README reviewed 25 November 2026. Repository snapshot: 12 November 2026, commit `892bb19`.**

## Membership, contributions and electoral planning

The free public resources remain open to anyone. The intended membership fee is cost-plus for hosting, storage, software and included AI upgrades, with processing costs and any agreed margin/reserve transparent. Organising, labour and campaign expenses do not belong in that fee. No fee, margin, AI allowance or provider has been agreed.

The stated organisational planning target is twice the qualifying membership minimum for state and federal party registration. Accounts, subscriptions, interest forms, working-group participation and qualifying political-party membership are different counts. Check the current electoral rules and required evidence for each jurisdiction; the finance and electoral readiness tools are scenario builders, not registration or filing services.

The 12 November finance work separates membership income, merchandise profit, donation scenarios, bequests, operating and campaign funds and the combined 12-month comparison. Each gift amount has its own donor assumption; merchandise uses adjustable profit bands. Detailed budgets start at zero, retain electorate-specific context and support local export through 2031. Assumptions and illustrative calculations do not constitute actual receipts, donations, forecasts or a campaign commitment.

**Financial transparency requirements:** the startup design evaluates two explicitly disclosed options: a named money ledger with membership-register disclosure separate, or a named money ledger plus a public membership register. Both require the same identity and independent admission standard. Explain the precise public fields and consent choices before real participation. The present fictional/demo receipt-level recognition controls are not a completed live transparency policy. Raw identity evidence, private contact data and financial credentials remain protected. No blockchain network, payment provider, token or live settlement is selected.

C-Hour recognition remains non-financial: one verified hour of freely given human time, counted once, with no money conversion. Personal agent-assisted contribution drafting starts from chosen evidence, clarification and participant review; L0 remains private and L1 is the first shared space. No automatic data sharing, extra voting entitlement or monetary reward is inferred.

## Private Cloudflare pilot

The private pilot implementation in [wrangler.pilot.jsonc](wrangler.pilot.jsonc) is designed for its own D1 database. The tracked template disables public routes and contains a placeholder binding ID; this README review does not inspect the private deployment. It starts with the configured organiser profile and empty working groups, projects and drafts. Changes persist across sign-ins. An organiser can create the first private working group and use it to start a project. Cloudflare Access restricts the workspace to the verified organiser aliases.

1. Create a dedicated D1 database named `p4a-membership-pilot`, apply [the pilot migrations](migrations/pilot/), and use its ID in an ignored local copy of the configuration. Resolve the entry point, assets and migration paths from the copy's location. The tracked template disables public routes.
2. Create a Cloudflare Access application for this Worker or its exact `workers.dev` hostname. Use an Allow policy with the invited email addresses and an authenticated sign-in method such as One-time PIN. Use a policy specific to the pilot.
3. Set `ACCESS_ISSUER` to the Zero Trust team URL and `ACCESS_AUD` to the application audience tag. Set `PILOT_ORGANISER_EMAILS` as a JSON array and `PILOT_ORGANISER_NAME` as the display name in Worker secrets. The aliases resolve to one organiser record. Keep these values out of tracked files.
4. Enable the pilot's `workers.dev` route once Access is set up. Verify signed-out protection and the signed-in workspace. The pilot database has a 1 MiB snapshot limit. Public member enrolment and live payments require their own setup. Reconcile an existing private deployment before creating any new database or Access application.

See [Cloudflare Worker Access](https://developers.cloudflare.com/workers/configuration/cloudflare-access/) and [application audience tags](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/#get-your-aud-tag).

## Hosting and Google storage

The required admission design now includes stringent KYC, substantive civic induction, independent review, and optional public name/membership/verification disclosures supported by zero-knowledge proofs. Blockchain integration is intended for credential trust, status and audit verification. These controls are **requirements, not implemented capabilities**; see [Identity and transparency](docs/IDENTITY-AND-TRANSPARENCY.md).

**Gamify Democracy** provides a local working contribution ledger and two separately measured leaderboards. Public names require an explicit choice for each receipt. Live payment settlement, cross-node credentials, ZKP and blockchain integration remain to be built; no token or network is selected. See [the contribution and leaderboard design](docs/GAMIFY-DEMOCRACY.md).

`wrangler.jsonc` describes a Cloudflare Worker plus static assets. `src/worker.mjs` uses the same application rules as the local server. Production contains no demo impersonation endpoint and fails closed when identity or storage is missing. The optional Cloudflare Access identity adapter verifies a token and maps it to a deliberately provisioned person; it does not settle the public member sign-in choice.

An interim private Drive folder and empty register have been prepared in the Google account Luke selected. Verified account/file references are in ignored `.local/setup/connection.json`. No fictional demo records were uploaded. The running application is **not yet connected** to that register.

The Google adapter uses signed requests, a serial writer and optimistic revisions against one private Drive JSON document. This provides a concrete Workspace integration to test, with a current 1 MiB protocol limit. It is replaceable as measured needs grow. It does not automatically share Google Docs with members or make Drive permissions follow application membership.

See the [membership onboarding guide](docs/ONBOARDING.md), [Google integration and identity setup](docs/WORKSPACE.md), [the concept mapping](docs/CONCEPTS.md) and [verification and remaining live setup](docs/BUILD-STATUS.md).

Payments are intentionally inactive: the operator, paid benefits, pricing, terms and provider remain undecided. A production billing integration, reconciliation and regulatory reporting workflows still need implementation before money is collected. The present transparency view is not a regulator filing service or an accounting ledger.
